## 目标

在不改变数值方法和结果的前提下，减少 NICE 部署实现的时间和内存（GPU 显存与主机内存），把单卡能算的胞元规模往上推，为后续大规模计算做准备。

- 目标硬件：导师采购的 RTX 4090 48 GB（魔改卡）加 128 GB 内存。
- 对照和验证：在现有的 RTX 5090 32 GB 机器上做。

## 候选改动（之前分析过，都还没实测）

### 甲类：算术不变，只差舍入顺序；时间和内存都省

**1. 三个已写好、默认关闭的开关**
- 开关：`OPL_KE_SYMV`、`OPL_COARSE_INV`、`OPL_KE_SYMV64`。
- 效果：单胞元 Ŝ 从 79.7 ms 降到 61.1 ms（−23%），输出差 4e-8；大胞元的临时单元刚度约减半。
- **问题：** 2026-09-28 在 92 胞元点阵里全开后，第 0 次迭代 63 分钟还没跑完，而全关时整轮只要 28.6 分钟。按 16 列分块也没解决，原因未查清。
- 当时排了 `chain_diag5.sh`，在 8 胞元 hlat222 上逐个开关测，但仓库里只找到全关一组的结果。详见 `docs/MORNING_REPORT_20260928_CN.md` 第 3 节。
- 先定位原因，再启用。

**2. 完全被材料填满的单元共用一个单元刚度**
- 这类单元的矩是闭式值，与厚度无关，所以刚度完全相同。`moments_ad.full_rows` 已经能识别它们。
- 占激活单元的比例估计：

  | τ | 0.18 | 0.40 | 0.55 | 0.69 |
  | --- | --- | --- | --- | --- |
  | 占比 | 约 1% | 约 32% | 约 45% | 约 56% |

**3. 每胞元状态瘦身**
- GPU 上：小于 1 MiB 的张量和元组里的张量不参与流式，每个流式胞元都在 GPU 上留了一份。
- 主机上有重复或位宽过大的数据：
  - 矩同时存了 fp64 和 fp32 多份；
  - 粗网格延拓矩阵和它的转置各存一份；
  - 𝕂_PP 三元组用 int64；
  - 几何原始数组一直留着。
- 状态变小后，每次 PCG 迭代的 PCIe 传输也随之减少。

**4. 𝕂_PP 装配**
- 改用 int32 和预分配的 CSR，去掉排序去重的大临时数组，降低显存峰值。

**5. 粗网格逆矩阵**
- 按对称打包只存一半。

### 甲'类：只省时间

**6. 流水化**
- 几何生成、胞元准备和 GPU 计算重叠。110 胞元时几何 71 s、准备 185 s。

**7. CUDA Graphs**
- 录制每个胞元的 Ŝ 作用后重放。先测核函数启动开销的占比，再决定做不做。

### 乙类：收敛解不变，但改了预条件子或缓存的精度（单独验证，单独报告）

**8. 𝕂_PP 用 fp32 分解**
- 因子显存减半。
- 风险：矩阵病态时分解可能失败，迭代次数可能变。

**9. 胞元粗网格矩阵直接 fp32 分解**
- 基准胞元缩放后的条件数是 163。

### 纯代码做不到的

- 𝕂_PP 分解随主自由度超线性增长。
- 时间与胞元数成正比。
- 要过 200 胞元，得换预条件子，不在本任务范围内。

**粗估（未实测）：** 时间快 1.3–1.8 倍；32 GB 卡的上限从约 115 胞元推到 150–200 胞元。

## 约束

**论文与原代码**
- 不改论文文件，即 `docs/paper_p1` 下的正文、补充材料、latex 和 word。P1 的计时来自现有代码，本任务的改动只用于后续工作。
- 不动论文用的代码，在副本上改（例如仓库里的 `docs/data/src_v3/`、机器上的 `/root/autodl-tmp/OPL/src_v3`）。机器上的 `src_v2` 保持原样，保证论文数字能复现。

**结果核对**
- 甲类改动必须保持结果不变：
  - PCG 迭代次数完全相同；
  - 柔度相对差 ≤ 1e-7（不同机器之间实测为 3.7e-8）；
  - 每胞元灵敏度相对差 ≤ 1e-6；
  - 单胞元 Ŝ 输出相对差 ≤ 1e-7。
- 每做完一项，都在 8 胞元 hlat222 上核对。
- 乙类改动单独做、单独报告，不和甲类的计时混在一起。
- 不用 fp16、bf16、TF32：保持 `OPL_CONV_FP32=1`，并关掉 TF32。

**计时**
- 同一时间只跑一个计时任务。
- 整卡显存用 nvidia-smi 每 0.1 s 采样（参考 `remeasure.sh`），同时记录 PyTorch 峰值、主机内存和各阶段时间。

**机器**
- 连接方式：Jupyter 内核 API 走 HTTPS，工具是 `docs/paper_p1/review_r1/remeasure_20261017/jrun.py`，从环境变量 JH、JT 读取地址和令牌。从云端会话用 SSH 连不通。
- 地址和令牌：用户在新会话的第一条消息里直接给出。只存在会话的临时目录里，不写进仓库（仓库是公开的）。机器重启后令牌会变，返回 403 时请用户重新把 `jupyter server list` 的输出用文字发来，不要从截图里读令牌。
- jrun.py 在内核里同步执行命令：长任务用 `setsid nohup ... &` 放到后台，写状态文件再轮询，否则会堵住之后的调用。
- 有的区域（例如 westc）从云端会话连不上，这时请用户在机器上开 Cloudflare 临时隧道。
- 正式的长时间 GPU 运行前先告诉用户。只停自己启动的进程。不租、不释放、不关机器。

**提交**
- 经常提交并推送。
