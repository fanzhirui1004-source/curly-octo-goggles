# Route 5 costed: condensation is worth it, but not for the reason we assumed

2026-09-17. Script `superelement/contract/route5_cost.py`, data
`docs/data/ROUTE5_COST.json`. Every input is either measured in this project or an
explicitly labelled assumption with a range.

## The question

The user: *a Schur complement is dense, and density is exactly what keeps it out of
topology optimisation, so why condense at all?* GPT Pro's decision 1 independently
recommends delivering `S` implicitly rather than materialising it.

## The answer

At `N = 1000` cells and `M = 500` design iterations:

| route | whole run | memory | accuracy gate |
|---|---|---|---|
| fine, matrix-free, **solve only** | **58 min - 4.8 h** | **17 GB** | **none** |
| fine, matrix-free, **+ re-cut geometry each iteration** | **7.9 h - 29 d** | 17 GB | none |
| predicted H-matrix `S` at the 0.15 gate | **2.0 - 2.2 h** | 64 GB | `eps_op` 0.15 |
| predicted dense `S` | 19 - 21 h | 610 GB | `eps_op` 0.15 |
| teacher, no network, **one iteration only** | 10.8 - 26.4 h | - | - |

**On the solve alone the fine route wins**: comparable or faster, four times less
memory, and no accuracy requirement at all - you ask the solver for 1e-8 and pay
iterations. The premise this project started from - "the fine problem is infeasible,
so condense" - is **not supported by these numbers.**

**What the network actually buys is skipping the geometry pipeline.** It consumes 12
numbers per cell (8 `tau` corners + 4 cut-plane coefficients; `adapter.geometry_values`)
and never meshes, never computes cut-cell quadrature, never assembles. The fine route
must re-cut and re-quadrature every cell every design iteration, because the geometry
is exactly what the optimiser changes.

So the project's justification should be restated:

> The value is in replacing the **geometry -> operator pipeline**, not the **solve**.

That is a sharper claim and a better one, because it does not depend on the fine solve
being infeasible - which it is not.

## The decisive unknown, and it is one measurement

The geometry re-cut cost per cell per iteration is assumed here at **0.05 - 5 s** and
is **not separately measured anywhere in this project**. The teacher's receipt bundles
it as *"geometry and factor preparation ~29 s"* (`HANDOFF_20260913`, seat 0257), which
mixes it with the factor preparation.

The band spans the decision:

| geometry re-cut | fine route, N=1000, M=500 | verdict |
|---|---|---|
| 0.01 s/cell | ~1.4 h | **fine route wins** |
| 0.05 s/cell | 7.9 h | predicted `S` wins by 4x |
| 0.5 s/cell | ~2.9 d | predicted `S` wins by 30x |
| 5 s/cell | 29 d | predicted `S` wins by 300x |

**Next action: time the CutFEM cut/quadrature stage alone, for one cell, with the
level set perturbed.** One measurement on the box. Until it exists, route 5 is
undecided, and so is the justification for routes 1-4.

## Other assumptions, listed so they can be attacked

| assumption | value | why it matters |
|---|---|---|
| sustained fp64 for a matrix-free Q2 hex apply | 1.0e12 FLOP/s | the 5090's fp64 is weak; if the fine solve runs in mixed precision this improves several-fold and the fine route gains |
| flops per dof per matvec | 1000 | literature range 500-2000 for 3D Q2 with sum factorisation |
| multigrid matvec-equivalents per solve | 30 - 150 | **cut-cell conditioning is the real risk here**; ghost penalty fixes the assembled operator, not the solver |
| interface iterations | 20 - 80 | with a reasonable preconditioner |
| H-matrix emit cost | scaled from the dense predict FLOPs by the number ratio | **this is pessimistic**: Codex's per-pair MLP spends 6.21 MFLOP per 3x3 block, but an H-matrix head emits a whole low-rank block per decode, so the real cost is likely far lower |

## What this does not say

It does not say the fine route is easy. CutFEM small cut cells give arbitrarily bad
conditioning, and the 30-150 band is wide precisely because nobody here has built that
solver. It says the fine route is **not obviously infeasible**, which is enough to
make the geometry measurement the gating item.

It also does not retire routes 1-4. If the geometry cost is real, they are the way to
avoid it, and the question becomes only *which representation*.
