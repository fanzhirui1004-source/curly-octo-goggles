# src_v3 改动记录

每项改动都在 8 胞元 hlat222 上核对（表 5 路线，FINAL3 参数，`scripts/t5.sh` / `scripts/census.sh`），并与原样 src_v3 的基线比较（`results/base`）。

## 核对标准与噪声底

- **PCG 次数**：必须完全相同。
- **柔度**：相对差 ≤ 1e-7。原代码重跑的噪声约 1e-8。
- **每胞元灵敏度**：交接文档要求相对差 ≤ 1e-6，但原代码本身重跑就达不到。
  - 原样 src_v3 重跑一次（`cen0`），与基线最大相差 1.83e-6；
  - 只开开关的三次运行，最大相差 1.4e-6 到 2.1e-6；
  - 噪声来自 index_add_、Triton 散射等原子加的求和顺序，以及 PCG 解约 1e-8 的差异。
  - 因此灵敏度按"不超出原代码的重跑噪声带（约 2e-6）"判定。
- **单胞元 Ŝ**：相对差 ≤ 1e-7（`scripts/v3_shat.py`）。

| 内容 | 文件 |
| --- | --- |

**fp32 修正不共用（OPL_FULL_KE32 默认 0）。** 实测发现，完全单元存下来的矩各不相同：64 个子立方体的项由原子加求和，顺序不定，所以每行的末位都不一样，fp32 舍入后每个单元也都是不同的位模式。无论共用哪一个 fp32 矩阵，都与各单元自己的 fp32 矩阵在许多元素上相差约 1 个末位单位，而且对上千个单元同向。

## S5：网络槽权重按需重算（可选，OPL_V3_SLOTS=recompute，默认不开）

FastNet 不再存各层的 a、b，只存几何嵌入 ge、gn（大胞元约 31 MiB；a、b 约 270 MiB）。每次应用时按 models.MGNO2.geometry 的原算式和原形状重算，用完即丢。

单胞元（hlat222_000，`results/s5`）：
- 输出与存储模式相差 7.9e-8，即两次进程运行之间的原子加噪声；
- 但每次 Ŝ 多 9.4 ms（B=1 时 30.9 → 40.3 ms，+30%），瞬时显存多约 1 GB。

S1–S4 之后，主机内存不再是第一约束：板胞元每胞元约 0.45 GiB，128 GB 可容纳约 270 胞元，先到上限的是 GPU 上的 cuDSS 因子。因此默认不开，主机内存紧张时再用。

## S6：cuDSS 混合内存模式的后备（默认 auto）

SPDSolver 在 plan 之后读取 cuDSS 的显存估计（permanent / peak / hybrid_min / hybrid_max）。如果规划的峰值显存大于当前空闲显存减余量（OPL_KPP_MARGIN_GB，默认 1.5），就改用混合内存模式重建：因子放在主机内存，设备用量限制在空闲显存以内。

- OPL_KPP_HYBRID=1：总是用混合模式；=0：从不用。
- 混合模式只改变因子存放的位置，分解和求解的算术不变。
- hlat222 上强制混合模式（`results/hy1`）：PCG 129 次，柔度差 1.0e-8，时间不变。

## S8：Chebyshev 扫掠融合（默认开，OPL_V3_CHEB=0 可关）

smooth_tail / _cheb 的每次扫掠原来是一次 fp32 K 乘积加约十个小的 fp64 PyTorch 核（整向量的类型转换、内部行收集、递推更新、非原地 index_add、清零）。现在每次扫掠是 fp32 K 乘积（作用于一个随迭代更新的 fp32 副本）加一个 Triton 核。fp64 递推与原 PyTorch 表达式的运算和顺序相同，关闭 FMA（enable_fp_fusion=False）；PyTorch 对"CUDA 张量 / Python 标量"实际计算的是乘以 fp64 倒数，这里同样乘以 1/theta。系数张量按 (theta, delta, k) 缓存：每次新建设备张量的主机到设备复制会让流同步。

核对（`scripts/t_cheb.py`，`results/tests1`）：
- 合成胞元（稠密 SPD 的 fp32 乘积，确定性 GEMM）：smooth_tail（fp32 / fp64 输入）、_cheb（B=1、5）、smooth_tail_T 与原 PyTorch 递推逐位相同；
- 板胞元 plateS24_040（确定性模式，OPL_KE_SYMV=0 使每次乘积可重复）：smooth_tail、smooth_tail_T 在 B = 1、3、16 时逐位相同；含网络和原子加的 field / Ŝ 与原路径之差等于原路径自身两次运行之差（Ŝ 6–8e-8）。
- 时间：B=1 的 Ŝ 约快 1 ms（30.8 → 29.8 ms），B=16 快 7%。

## S9：fp64 部分单元刚度只算一次（默认 OPL_V3_KE64=store，=form 恢复原行为）

每次 Ŝ 有一次 fp64 K 乘积，原来每次都用 fp64 GEMM（部分单元数 × 125 × 3321）从矩重算部分单元的打包刚度；5090 的 fp64 只有 fp32 的 1/64，这一步约占 Ŝ 的 4 ms / 31 ms。现在每个设计在预热后算一次并随胞元状态保存（流式胞元在锁页主机内存，常驻胞元在显存），用的是同样的分块和同样的 GEMM，所以乘积不变。代价：每个部分单元 8 × 3321 字节，板的满胞元约 206 MB（主机内存紧张时用 =form）。

核对（`scripts/t_ke64.py`，plateS24_040）：保存的矩阵与重新计算的逐位相同（2 块，197.5 MB）。Ŝ：B=1 29.75 → 25.65 ms（−14%），B=3 47.8 → 43.8 ms，B=16 216.5 → 212.5 ms；输出差 7.0e-8，与同一路径两次运行之差相同。

## S14：每胞元可选项的主机内存预算（默认开：OPL_V3_KE64=auto、OPL_V3_SLOTS=auto）

`hostmem.Budget` 在前端每个胞元预热后重新规划：
- 预算 = 0.85 × 上限（cgroup memory.max 或物理内存），减去当前 RSS，再减去这个胞元和其余每个胞元的基本状态（取这个胞元预热后的显存占用，扣掉槽权重）；
- 剩下的先给槽权重，够所有剩余胞元时再给 fp64 刚度；
- 先处理的胞元先得到。

0.85 的依据：51–162 胞元的板上，一次分析的 RSS 峰值约为前端结束时 RSS 的 1.1 倍（之后还有 K_PP 装配、格架、cuDSS、灵敏度）。

- 135 胞元板（`results/v3g_S135`）：槽权重 135 个全部保留，fp64 刚度保留 73 个；PCG 172，柔度与 v3a 差 3.9e-8；一次分析 1098 → 816 s；主机峰值 82.3 GiB（上限 90），显存峰值 19.4 GiB。

## S15：胞元粗网格逆改为分块结构（默认开，OPL_COARSE_BLK=0 恢复 S2 的打包逆）

S2 之后，打包的 fp32 粗网格逆（nc²/2 个数，满胞元 168 MiB）是流式状态里最大的一项。粗网格矩阵 A_c（Q1_17 粗空间，Jacobi 缩放）只耦合相距不超过 w 个顶点间距的顶点（w 从矩阵的非零元读出；板胞元因鬼面罚项 w = 2）。每个轴上取中间宽 w 的一层顶点作分隔层，其余顶点分成互不耦合的 8 个卦限。按这个分隔做分块消元（精确）：

- y_o = A_oo⁻¹ z_o（各卦限独立）；
- x_s = S⁻¹ (z_s − Σ A_so y_o)，S = A_ss − Σ A_so A_oo⁻¹ A_os 是分隔层上的 Schur 补；
- x_o = A_oo⁻¹ (z_o − A_os x_s)。

卦限逆和 S⁻¹ 用 fp64 Cholesky 算出、存成 fp32 打包对称块（8 个卦限合成一个块对角块表，一次 Triton 调用）；A_os 存成 fp32 CSR。算术上与显式逆相同，只是 fp32 舍入不同。与打包逆一样，用 4 个随机向量和 fp64 解核对（OPL_COARSE_INV_TOL = 1e-4），不合格就退回打包逆。分块省不到一半的小胞元仍用打包逆。

核对（`scripts/t_cblk.py`，`results/tests10/cblk.log`；同一胞元分别用两种方式建立）：

| 胞元（粗自由度） | 粗网格存储 MiB | 对 fp64 解的误差 | Ŝ 相对差 | 粗网格求解 ms（B=1） |
| --- | --- | --- | --- | --- |
| 满胞元（9324） | 167.7 → 29.1 | 2.9e-7 → 1.7e-7 | 3.7e-8 | 0.39 → 0.26 |
| 切割胞元（8916） | 154.2 → 26.9 | 2.9e-7 → 1.8e-7 | 2.7e-8 | 0.36 → 0.26 |
| 切割胞元（6318） | 77.3 → 16.6 | 1.6e-7 → 1.6e-7 | 2.6e-8 | 0.23 → 0.26 |
| 小胞元（819） | 1.4（仍用打包逆） | — | 2.1e-8（重跑噪声） | 不变 |

- 分块的误差比打包逆还小，因为各块在 fp64 中算出后只舍入一次。
- Ŝ 时间不变（满胞元 B=1：25.2 → 25.0 ms），每胞元预热时间约 −0.06 s，建立时 PyTorch 峰值 −0.4 GiB。
- hlat222（与 S16–S18 一起，`results/v3h_t5`）：PCG 129，柔度与原代码差 1.9e-8，每胞元灵敏度差 2.27e-6（噪声带内），一次分析 49.3 s（原代码 77.0 s）；每个胞元变小，8 个胞元全部常驻显存（原来 4 个），显存峰值 8.25 GiB（原代码 10.53），前端后主机 2.65 GB（原代码 4.10）。

## S16：K_PP 主机三元组装配后即释放（默认开，随 OPL_V3_SLIM）

驱动程序（opt_design、lat_scale）在前端把每个胞元的 K_PP 上三角三元组放在主机上（int32 行列、fp64 值，满胞元约 10 MB），格架装配 K_PP 时读取。装配后它们不再被读取，原来一直留到这次分析结束。现在 MultiLattice 在装配完所有胞元的三元组后调用驱动给的释放函数，在 cuDSS 规划之前释放（135 胞元 1.7 GiB，162 胞元 2.0 GiB），主机峰值相应降低。算术不变。

## S17：前端每胞元的垃圾回收只收年轻代（默认开，OPL_V3_GC=full 恢复原行为）

前端每个胞元调用四次 gc.collect()（assemble_deploy 两次、_free 一次、驱动一次），每次完整回收要遍历所有存活对象，约 40–110 ms。每个胞元的临时数据由引用计数释放，不需要完整回收。现在这四处只回收年轻代（gc.collect(1)），前端结束后做一次完整回收。算术不变；显存释放的时机可能略晚，前端显存只用约 8 GiB，不受影响。

实测（`scripts/t_prep.py`，24 胞元板的 5 个胞元，取后 4 个的平均，`results/tests10/prep_gc*.log`）：每胞元前端 1.391 → 1.114 s（−20%），其中 assemble_deploy 0.462 → 0.247 s，驱动的回收 0.054 → 0.000 s。S15 的分块粗网格逆使预热多 0.055 s、锁页少 0.03 s，合计每胞元 1.132 s。

## S18：宽作用中流式胞元只复制一次

格架粗空间 A Z 对每个胞元作用 48 列，按 16 列分三块。原来每块都单独进入、离开流式胞元的作用域，同一个胞元从主机复制到显存三次（每次约 14 ms，后两次不能与计算重叠）。现在三块在同一个作用域里，只复制一次。算术不变。

### PCG 矩阵向量乘的瓶颈（`scripts/t_prof16.py`、`scripts/t_graph.py`）

- 满胞元 B=1 的一次 Ŝ：单流时 GPU 自己就要约 19.5 ms（用 CUDA 图重放也是 19.47 ms，与即时执行的 19.65 ms 几乎相同），所以单流是 GPU 受限的。
- 两个流时，51 胞元板每胞元约 16.7 ms，比单流只快 17%：这时 CPU 每胞元要发约 1400 次核启动（16–18 ms），成了瓶颈。下面的 S20、S24 都是减少核启动次数；S26 用 CUDA 图把一次作用变成一次启动。
- 一个核启动的 CPU 开销（`results/tests13/launch.log`）：Triton 13.7 µs，PyTorch 的逐元素/索引/小矩阵乘 5–9 µs。

### S19：重算槽权重时头部的缩放和软截断合成一个 Triton 核（默认开，OPL_V3_SLOTFUSE=0 可关）

槽权重不保存时，每次作用都要重算（S5/S14）。原来每个头的输出要经过约 11 个逐元素核（×0.2、软截断）。新核按同样的 fp32 运算顺序一次算完，关掉乘加融合，IEEE 除法和 libdevice tanh 与 PyTorch 相同。

核对（`scripts/t_slotfuse.py`，`results/tests12/slotfuse.log`）：ab、fab、xab 三个输出逐位相同（约 1 亿个数）；`_slot_tensors` 7.8 → 3.2 ms，连同赋值 9.4 → 4.8 ms（每次重算）。

### S19b：重算后的槽权重一次赋给各层（可选，OPL_V3_SLOTASSIGN=1，默认不开）

单元层和 g < L 的鬼面层的 a、b（含 B3 折叠 b·(1 + λ·fac)）各用一个 Triton 核写出。24 层逐位相同，但赋值只从 1.67 ms 降到 1.60 ms（时间主要在内存读写，不在核启动），所以不默认打开。

### S20：鬼面罚项乘积的自由度数组拼接（默认开，OPL_V3_GFCAT=0 可关）

鬼面乘积原来按三个方向各自收集、相乘、散射，每次 12 个核。现在三个方向的收集索引拼成一个数组，一次收集、按方向两次矩阵乘、一次散射，共 8 个核。各方向的视图在用时才切出（不另存，否则流式状态里每胞元多约 10 MiB）。

- 单流 Ŝ 不变（25.07 → 24.79 ms，GPU 受限）；两个流的 51 胞元板求解 160.2 → 149.2 s（−7%），一次分析 280.5 → 270.8 s，PCG 168 不变，柔度差 3.1e-9（`results/v3m_S51`、`v3n_S51`）。
- 另试了把三个方向补齐到同一大小、用批量矩阵乘（S20b，OPL_V3_GFBMM=1，4 个核）：板的时间相同（149.0 s），hlat222 反而慢（48.6 → 51.8 s），不采用。

### S21：cuDSS 分解后释放 K_PP 的 CSR 矩阵（默认开，OPL_V3_KPP_FREEA=0 可关）

求解阶段只读因子（没有配置迭代修正），所以分解后把 CSR 的三个存储（int32 行指针和列号、值）释放，每个上三角非零元约 12 字节显存（192 胞元约 1.4 GB）。

核对（`scripts/t_kppfree.py`，`results/tests15/kppfree2.log`；51.2 万未知数、203 万非零元的 SPD 矩阵）：
- 释放前后同样右端的解相差 3.6e-15（|y| 约 10）；不释放、连解两次也相差 4.4e-15，因为 cuDSS 的求解本身不是逐位可重复的。
- 释放后把所有空闲显存块填成 NaN 再解，结果仍有限，差 3.6e-15：求解确实不读矩阵。

### S22：粗空间保留的列不经过 V 判定（默认开，OPL_V3_COARSE_COLS=0 可关）

coarse_prolong 先组出整个延拓矩阵 V，再按列和判断保留哪些粗顶点。新函数用同样的帽函数权重（同样的浮点运算），按 bincount 求内部行的 |w| 列和。保留的列的列和至少是 (1/R2)^3，丢掉的列是 0 或约 1e-16，离 1e-14 的阈值很远，所以保留集合相同。

核对（`scripts/t_coarsecols.py`，`results/tests14/coarsecols.log`）：4 个板胞元保留的列完全相同；每胞元 0.15 → 0.05 s。

### S23：常驻胞元显存预算自动确定（`--resident-gb auto`，默认仍为 4）

常驻胞元（不流式）不占主机内存。auto 按显卡总显存减去固定项 3.5 GiB、每胞元 0.054 GiB（粗空间 A Z、K_PP 因子等，按 51–192 胞元板测出）和 3 GiB 余量。

51 胞元板（`results/v3r_S51`，同时开 S21、S22、S24）：常驻预算 22.1 GiB；一次分析 260.3 → 248.4 s（−4.6%）；主机峰值 27.0 → 9.6 GiB；PyTorch 显存峰值 27.2 GB，nvidia-smi 31.7 GB，离 32 GB 已很近。所以默认不开，只在容量测试里用（主机内存是瓶颈时，常驻胞元把这部分转到显存）。

### S24：网络前向/伴随中合并核启动（默认开，OPL_V3_NETFUSE=0 可关；netfused.py）

三组合并，每组都是同样的值、同样的 fp32 运算：
- 前向层加端口钳位：where(端口, X0, X + S Z) = where(端口, X0, X) 再在非端口行加 S Z；散射直接加到钳位后的副本上并跳过端口行。3 个核变 2 个。
- 伴随层的掩码：X0b += where(端口, Xb, 0) 和 A = where(端口, 0, Xb) 一个核完成，层的散射原地加到 A 上。
- U-Net 卷积：密网格输入（清零 + index_copy_，转置卷积还要先乘门控）一个核，输出 Xc + v[dense_idx]（× 门控）一个核；cuDNN 调用本身不变（同样的输入布局和值）。

核对（`scripts/t_netfuse.py`，`results/tests15/netfuse2.log`，满胞元）：
- 设 torch.backends.cudnn.deterministic 后，48 个卷积（正向和转置，B=1、3）与原路径全部逐位相同。默认设置下转置卷积连原路径自己重跑也不逐位相同（cuDNN 选的算法），这是原来就有的。
- 带原子操作的层：新旧之差与原路径自己重跑之差相同（4–9e-8）。
- Ŝ：B=1 20.6 → 19.7 ms，B=3 40.9 → 37.1 ms。
- 51 胞元板（与 S21、S22 一起，`results/v3p_S51`）：一次分析 270.8 → 260.3 s，其中预处理 34.5 → 30.2 s（宽作用 A Z 受益），前端 55.9 → 50.5 s；PCG 168，柔度差 8.1e-9。hlat222（`results/v3p_t5`）：48.6 → 44.6 s，PCG 129，柔度差 2.0e-8，灵敏度差 2.2e-6（噪声带内）。

### 第二类（结果不逐位相同，单独报告）：K_PP 因子用 fp32（OPL_V3_KPP_FP32=1，默认不开）

K_PP 的 cuDSS 分解和回代用 fp32（PCG 本身仍是 fp64，K_PP 只作预条件）。
- 合成矩阵上与 fp64 因子的解相对差 1.8e-6；cuDSS 估计的常驻显存 3.45 → 2.01 GB。
- 51 胞元板（`results/v3q_S51`）：PCG 168 不变，柔度与 v3f 差 1.4e-8（与噪声同量级）；nvidia-smi 峰值 15.8 → 14.7 GB；但求解没有变快（148.6 → 154.1 s）。hlat222：PCG 129，44.6 → 44.1 s。
- 结论：只省约 1 GB 显存，不提速；显存不是这台机器的瓶颈，所以不采用。

### S25：K_PP 规划峰值时把停放的胞元状态暂存到磁盘（OPL_V3_SPILL=1；用后预算不再预留）

K_PP 的 cuDSS 规划和分解在主机上有约 15 s 的瞬时量（每个装配后非零元约 71 字节，192 胞元 8.6 GiB）。S14b 为此在前端预算中预留 4 倍三元组字节，这部分内存在前端期间不能放胞元。现在在规划和分解外面加一个保护（stream_ops.spill_guard）：若当前 RSS 加上估计的峰值（每个上三角非零元 80 字节）超过上限的 0.95，先同步设备、停放所有状态，然后把最大的若干个停放胞元的锁页缓冲写到磁盘文件（写完 fsync 并丢弃页缓存，免得页缓存占容器内存），释放；分解完成后读回到新的锁页缓冲，删除文件。字节完全相同。打开后 OPL_V3_HOST_TRANSIENT 默认为 0，预算不再预留。

核对：
- `scripts/t_spill.py`（`results/tests16/spill.log`）：含 fp64、fp32、int64、稀疏 CSR 的状态，暂存再读回后每个张量逐位相同；RSS 按字节数释放和恢复；文件删除；写 0.84 GB/s，读 1.41 GB/s。
- 51 胞元板强制暂存 6 GiB（`results/v3t_S51`，OPL_V3_SPILL_FORCE_GB=6）：11 个胞元，6.2 GiB，写 8.8 s、读 4.5 s；PCG 168，柔度与不暂存的 v3s 差 2.9e-9；主机峰值 27.1 → 25.1 GiB。
- 代价约每 GiB 2 s。192 胞元时需暂存约 9 GiB（约 18 s，一次分析的 1.4%），换来前端多约 9 GiB（约 20 个胞元的最小状态）。

### S26：窄作用（PCG 矩阵向量乘）用 CUDA 图（OPL_V3_GRAPH=1；cellgraph.py）

每个胞元每种宽度（≤ 4 列）、每个流各捕获一个 CUDA 图，之后每次作用只是一次重放：同样的核、同样的参数，只少了 CPU 的约 1400 次启动。
- 流式胞元的图从锁页主机缓冲复制状态到图的内存池、解码、绑定、再算 Ŝ，所以重放不需要固定地址的显存缓冲；一个胞元的复制与其他流的计算并行。主机缓冲若移动（S25 暂存后读回），重新捕获。
- 在同一个流上重放的图共用一个内存池（每次重放后中间量都已无用）；每个重放流有自己的捕获流。后者是必须的：cuBLAS 的工作区按（句柄，流）分配，捕获的 GEMM 记住的是捕获流的工作区；两个共用工作区的图在两个流上同时重放会挂起（stream-K GEMM 通过工作区同步）。原型第一次就是这样挂起的，改为每个重放流一个捕获流后不再挂起。
- 第一次窄作用照常执行（编译核、建缓存），第二次捕获。PCG 后释放所有图和内存池，灵敏度阶段不受影响；S23 的自动常驻预算为每个流的内存池预留 1.75 GiB。

核对（`scripts/t_graph.py`，`results/tests17/graph3.log`）：
- 单胞元 B=1、3，槽权重保存或重算：重放与即时执行之差 3.5–3.9e-8，与即时执行自己重跑之差相同；捕获每个约 0.07 s，主机内存可忽略。
- 单流时没有收益（19.65 → 19.47 ms：单流 GPU 已满）。四个胞元轮流放在多个流上：

| 流数 | 即时执行 ms | CUDA 图 ms |
| --- | --- | --- |
| 1 | 65.0 | 60.3 |
| 2 | 63.2 | 51.8（−18%） |
| 3 | 63.1 | 52.1 |
| 4 | 61.7 | 47.3（−23%） |

51 胞元板（`results/v3u*`、`v3w`、`v3z*`）：
- 第一次跑的两组（v3u、v3v）一个图也没捕获：PCG 不在 no_grad 下运行，资格检查却要求自动求导关闭。改为按输入是否需要梯度判断、捕获在 no_grad 下进行之后，每次 102 次捕获、8517 次重放、0 次失败。
- 图里自己复制流式胞元状态（OPL_V3_GRAPH_STAGES=0）：两个流时求解反而变慢（159.1 s），因为复制和计算在每个流上交替，不能像即时执行那样提前在复制流上预取。四个流 139.9 s。
- 改为分段缓冲（默认 4 个，按预取环位置轮用）：状态在复制流上提前复制到固定的显存缓冲，图只做解码和计算；复制流在每个缓冲上一次重放结束后才覆盖它。两个流求解 141.1 s，四个流 138.6 s；同配置的即时执行 148–155 s（这几次即时执行之间就差约 4%）。PCG 都是 168，柔度差 ≤ 3.3e-8。
- 收益比四胞元测试小，是因为整块板时 GPU 已接近满载：矩阵向量乘中位数 0.85–0.89 → 0.81 s（两个流）、0.79 s（四个流）。hlat222（8 个常驻胞元）没有变化（45.0 s）。
- 默认开，两个流（四个流再快 2%，但多两个内存池约 2.6 GB）。

### S27：U-Net 转置卷积改用等价的正向卷积（默认开，OPL_V3_CONVT=0 恢复 cuDNN 转置卷积）

步长 1、填充 1 时，conv_transpose3d(x, W) 等于 conv3d(x, W')，W' 交换输入/输出通道并把 3×3×3 核翻转。权重每个模型只算一份（各胞元共用，不进流式状态）。cuDNN 在这里为转置卷积选的算法比正向卷积慢约 3.5 倍，而且不可重复（见 S24 的核对）。

核对（`scripts/t_convt.py`，`results/tests19/convt.log`，满胞元，36 个卷积 × B = 1、3、16）：
- 每个卷积与 cuDNN 转置卷积的相对差最大 1.6e-6（fp32 求和顺序不同），cuDNN 自己重跑最大差 3.5e-7；新卷积每次结果相同。
- 36 个卷积合计 21.7 → 7.8 ms。
- Ŝ：B=1 19.7 → 19.6 ms，B=3 37.2 → 35.5 ms，B=16 181.7 → 169.6 ms；与原路径之差和原路径自己重跑之差相同（3.8e-8）。
- 51 胞元板（与 S26 一起，`results/v3y_S51`）：预条件（A Z）30.1 → 28.6 s，PCG 168，柔度差 1.6e-8。hlat222（`results/v3y_t5`）：44.7 → 42.4 s，PCG 129，柔度差 1.5e-8，灵敏度差 2.3e-6（噪声带内）。
- 与原结果的关系：单个卷积的舍入改变比 cuDNN 自身的不可重复性大，但到 Ŝ 和最终结果都在原代码的噪声带内，与 S4、S10 同类（舍入级）。

### 讨论过、没有做的想法

- **K_PP 符号分析提前或复用**：目的是避开前端结束时主机内存最紧的时刻。S25 用暂存达到同样效果，而且不改变计算。复用（下一轮设计只做数值分解）要求 K_PP 的稀疏结构不变，而每轮设计的胞元几何不同，不适用。
- **每胞元状态再瘦身**：满胞元流式状态 606 MB，其中可选项 471 MB（fp64 单元刚度 198、槽权重 273），必需部分约 165 MB。剩下能去掉的，如 P/Pᵀ、R/Rᵀ 两份（共 13.7 MB）、粗网格分块的再一层剖分（约 10–15 MB），合计不到 10%，不值得承担新的舍入差别。
- **胞元粗网格的多层剖分**：分块粗网格已从 168 MiB 降到 28 MiB，再分一层约省一半，即每胞元约 14 MB（必需部分的 8%）。
- **前端流水**：几何生成与前端重叠已在 S12 做了。格架前端每胞元约 1.1 s，主要是 GPU 上的装配和预热，多线程重叠估计只能省约 4%，而且要处理线程间的 CUDA 状态，未做。
- **四个计算流**：见 S26。
- **K_PP fp32 因子**：第二类，见上，只省显存。

## 第三轮（P0–P10）：按剖析结果逐项试

### P0：剖析（`scripts/t_kprof.py`、`t_prep.py`、`t_sens.py`，`results/tests23`；`gpuprof.py`）

- Ŝ（满胞元，B=1）核时间 19.4 ms，约 1000 个核。按核：fp32 单元刚度乘积 6.3–6.8 ms（38 次，每次读 151 MB 打包刚度），超图层收集/散射 2.5 ms，U-Net 卷积 2.2 ms（cuDNN 选的是通用的 implicit_convolveNd_sgemm），鬼面罚项乘积的小 GEMM 和 index_add 约 2.8 ms，其余为大量小核。
- 板求解一次矩阵向量乘（51 胞元）的器件剖析（`OPL_V3_PROF_ITER=k`，`results/v3Q_S51/prof20_census_eager.json`）：第 20 次恰是 census 用来记时间线的即时、单流迭代，不代表求解；但核预算可用：每胞元 18.3 ms 核时间，流式胞元 24 GB 主机→显存复制 441 ms（54.7 GB/s），与计算重叠。正常迭代（图、两个流）0.80 s，核时间 0.94 s，两个流重叠约 1.17 倍，GPU 基本满载。所以求解只能靠减少核的工作量。

### P1：PCG 次数（第二类，默认不开）

- 现有粗空间：q1a 把 hlat222 的 PCG 从 129 降到 112，但粗空间建立更贵，总时间不变；pu12、加法式更差。
- 预条件后算子的 Ritz 值（`OPL_V3_PCG_LANCZOS=1`）：hlat222 条件数约 329，51 胞元板约 588，小特征值连续分布（板上 34 个低于最大值的 10%），不是少数离群值。
- Ritz 向量缩减重启（`OPL_V3_PCG_RITZ=m,k`，`lat_precond.rpcg`）：单个右端项时理论上不会少（CG 已隐式压掉收敛的 Ritz 值）；合成问题上确实一次不少（141 → 141）。多右端项时因为各列共享 Ritz 向量才有收益：hlat222（3 个载荷工况）129 → 119（40,10）、114（60,20）次。
- 块 PCG（`OPL_V3_PCG_BLOCK=1`，`lat_precond.bpcg`，无中断形式）：三列共用一个块 Krylov 空间，每步算子作用次数不变。hlat222：129 → 111 次，求解 26.1 → 22.9 s（−12.5%），整轮 41.2 → 38.0 s，三个柔度与默认相差 1–3e-8（与重跑噪声同量级）。板只有一个载荷工况，用不上。

### P2：fp32 单元刚度乘积核（默认开 OPL_V3_SYMV2，但实际没有提速）

- 单读核（每个打包上三角行块只读一次）在背靠背微基准里 168.5 → 120.9 µs；在 Ŝ 的 CUDA 图重放里没有变化（38 次合计 6.8 vs 6.6 ms，`results/tests27/symv3.log`），51 胞元板和 hlat222 的求解时间也不变（`results/v3P2_*`）。原因：微基准里同一个 151 MB 矩阵连续调用时部分留在 L2；Ŝ 里每次调用之间有别的核，矩阵每次都要从显存读，实测只有约 840 GB/s。
- 冷 L2（每次调用前改写 256 MB 缓冲）的扫描（`scripts/t_symv4.py`，`results/tests28/symv4.log`）：单读核 32 行块、1 个 warp 98.8 µs，旧核 147 µs，现默认 104.5 µs；但这个排序与 Ŝ 内的结果仍不一致，所以改为直接在 Ŝ 的图重放里比较各配置（`scripts/t_symv5.py`，测试中）。
- P2b（满单元的 fp32 刚度若与代表逐位相同就共用一行，`OPL_V3_KMAP`）：不适用。板胞元 3596 个满单元的 fp32 矩各不相同（fp64 矩只在最大元素的 1e-12 内一致，小元素在 fp32 精度上不同），没有可以共用的行（`results/tests28/kdedupe.log`）。强行共用就是以前测过的、使柔度变 3e-6 的那种系统性改变。

### P5：前端下一个胞元的 CPU 部分放到工作线程（默认开，OPL_V3_FE_THREAD=0 可关）

### P13：fp32 刚度乘积不用单元矩阵（OPL_V3_KMF，**默认开**；第二类：结果变化约 3e-6～7e-6，方向是回到 fp64 参照）

- 单元刚度是矩拟合的 Q2 单元：K_e = Σ_m M_e[m] T_m（125 个单项式矩）。被积函数在每个局部坐标上不超过 4 次，5 点 Gauss 积分精确，所以取 w_e = V⁻¹ M_e（125 个张量 Gauss 点上的拟合权重，fp64 算后取 fp32），K_e = Σ_q w_e[q] B_qᵀ C B_q 与原矩阵在精确算术下相同（fp64 检查 8e-15）。乘积每个单元只读 125 个权重和 27 个节点号（约 0.6 kB），不再读 3321 个打包元素（13.3 kB），也不用每次 Ŝ 先做 E×125×3321 的 GEMM 生成矩阵。
- 在随机切割盒上，fp32 下两种形式对 fp64 的误差相当（中位数都约 3e-7，最大值 1.1e-6 对 6.7e-6）。
- Triton 写法（125×27 导数表做 fp32 点积，每单元约 7.4 万次乘加）在 Ŝ 里每次 413 µs，比现有 183 µs 还慢，只作后备。
- 现在的实现是 CUDA C++ 核（`kmf_kernel.cu`，首次使用时用 nvcc 编译并缓存，ctypes 在 torch 当前流上启动）：和因式分解，每单元 25 个线程、约 1.24 万次乘加。鬼面罚项也改为无矩阵的核：模板满足 B_d = b_d ⊗ I_3（已核对），每个分量用 45×45 的 Gram 矩阵 γ b_dᵀ b_d；面的 45 个节点由两个相邻单元的节点表得到，每个面只读 8 字节索引（原来 540 字节）。numpy 逐线程转写的核与 fp64 参考相差 1.5e-8（单元）和 2.5e-8（鬼面）。只用于不超过 2 列的乘积（PCG 的矩阵向量乘），宽乘积仍用原矩阵。
- 单独测（满胞元，冷 L2，`results/tests32/kmf.log`）：单元乘积 B=1 104.2 → 13.9 µs，鬼面罚项 109.7 → 32.9 µs；对 fp64 的误差 1.45e-7（现有路径 3.54e-7）。Ŝ 图重放（`sw_kmf2`）：B=1 17.68 → 9.38 ms（−47%；只换单元乘积 11.76 ms），开/关输出差 7.8e-8（重跑 3.7e-8）。
- 多列版本（每块最多 4 列，`OPL_V3_KMF_MAXB=4`）第一次编译失败（模板放在 extern "C" 里），tests33 里 OPL_V3_KMF=1 的整轮其实走的是 Triton 后备：hlat222 柔度变了 3.2e-6（那种写法比现有路径还不准），说明 fp32 修正里的**系统性**舍入会被放大到柔度上（重跑噪声约 1e-8）。所以加了检查开关 OPL_V3_KC64=1（修正里的 K 乘积用 fp64 算再取 fp32）作参照，看新旧 fp32 路径谁离它近（tests34）。
- **柔度对照（tests34，hlat222 三个载荷工况）**：修正里的 K 乘积改用 fp64（OPL_V3_KC64=1，检查用）得到的柔度作参照。现有 fp32 路径（之前所有运行都一样）相对参照偏 −3.2e-6 / −1.7e-6 / −3.2e-6；无矩阵乘积（CUDA，Gauss 点）只差 −1.7e-8 / +1.1e-9 / −2.9e-8。也就是说，现有 fp32 打包矩阵路径本身有一个系统性的 fp32 误差（单项式模板在 fp32 里相消，见 `scripts/t_kmf_bias.py`：光滑场上能量相对误差 2.5e-5），无矩阵乘积把它去掉了，柔度回到 fp64 参照附近。结果不是逐位相同（变了约 3e-6），但方向是向精确值靠拢；单列表在“第二类”里另行报告。hlat222 整轮 37.5 → 35.2 s（求解 23.0 → 20.7 s），PCG 次数不变（129）。
- 减少系统性舍入的办法（下一步）：拟合权重时 5 个点不必是 Gauss 点，任意 5 个不同点都精确；取等距点 {−1, −½, 0, ½, 1} 时 Q2 形函数和导数的表值是二进制有限小数，fp32 里精确，系统性的表舍入就没有了；λ、μ 也并进每单元的权重（每单元各自舍入，不再是全体一致的偏差）。

- tests35：等距点的单元乘积对 fp64 误差 9.2e-8（Gauss 点 1.45e-7），速度相同；鬼面罚项的按自由度并行核（gf2，每个面 135 个线程，一个 warp 的收集和原子加落在连续的自由度上）在 2/3/4 列时 65/115/152 → 57/99/106 µs，单列时反而慢（31.6 → 39.7 µs），所以只在两列及以上用（OPL_V3_KMF_GF2=auto）。无矩阵乘积放宽到 16 列（OPL_V3_KMF_MAXB=16）：Ŝ 里有些乘积比输入更宽（如 B=3 时一次处理 6 列），原来要临时生成矩阵；B=3 26.7 → 24.2 ms，B=16 136.0 → 133.7 ms。
- 51 胞元板（OPL_V3_KMF=1，Gauss 点）：222.0 → 176.1 s，求解 126.9 → 82.7 s，PCG 168 次不变；柔度变 +1.7e-5（方向由下面 24 胞元板的 fp64 参照确认）。
- **板算例的 fp64 参照（tests35，24 胞元板）**：修正里的 K 乘积用 fp64（OPL_V3_KC64=1）得柔度 94.34132020；原默认 94.34066217（偏 −7.0e-6），P13 + P14（等距点）94.34132051（偏 +3.2e-9）。hlat222 等距点：三个柔度离参照最多 2.1e-8（原默认 3.2e-6）。两个算例都说明 P13 改变的那部分正是原 fp32 打包路径的系统性误差。所以 P13 改为**默认开**（`OPL_V3_KMF=0` 回到原路径），归入第二类单独报告。kmf.use()：开关开且 CUDA 库能编译时才用；没有 nvcc 时用原来的打包矩阵（Triton 写法比它慢，不再作为求解里的后备）。
- 24 胞元板整轮（同一批）：102.0 → 70.8 s（求解 57.7 → 29.4 s，每次矩阵向量乘中位数 0.324 → 0.158 s），主机峰值 11.6 → 8.3 GiB，PCG 169 次不变。51 胞元板等距点 153.9 s（Gauss 点 151.4 s，在重跑波动内），柔度两者相差 4e-9。

### P14：fp64 刚度乘积也不用单元矩阵（OPL_V3_KMF64，**默认开**）

同一个和因式分解核的 fp64 版本：部分单元用 fp64 权重做无矩阵乘积，满单元仍用 fullke 的共享矩阵 GEMM，鬼面罚项用 fp64 的 45×45 Gram 矩阵。这样 store64 不再需要存部分单元的 fp64 打包矩阵（板胞元每个约 206 MB，占胞元状态的三分之一；51 胞元板约 10 GB 主机钉页内存），hold64 也不用临时生成。

51 胞元板（P13 + P14）：222.0 → 151.4 s（求解 126.9 → 63.6 s，前端 43.2 → 38.7 s），主机峰值 27.0 → 19.0 GiB，流式状态 21.9 → 13.8 GiB，整卡显存峰值 15.6 → 13.0 GiB；柔度与只开 P13 时相差 4e-10。hlat222：37.5 → 34.4 s，显存峰值 8.96 → 8.07 GiB。没有 nvcc 时（库编译失败）自动退回原来的存矩阵路径。

tests34（`results/tests34/kmf64.log`、`sw_kmf64.log`）：与现有 fp64 乘积相差 2.4e-15（fp64 舍入级）；每次乘积 B=1 1155 → 469 µs（其中鬼面罚项 665 → 174 µs），B=16 13.0 → 7.1 ms；每个板胞元的 fp64 单元/鬼面数据 209 MB → 9.6 MB。Ŝ 图重放（在 P13 之上）：B=1 9.60 → 8.90 ms，B=16 142.2 → 136.0 ms，开/关输出差与重跑噪声相同（3.5e-8）。
